## Overview

This is the site you are reading. It is also the project I would point at first in a technical interview, because it is the one where I can show you numbers instead of adjectives.

The visible half is a Next.js front end. The interesting half is the chatbot in the corner: a Retrieval-Augmented Generation system that answers questions about my experience from my own resume and a written Q&A corpus, streaming responses through a FastAPI backend. Plenty of portfolios have a chatbot bolted on. What I wanted was the thing most of them skip — a way to know whether the retrieval underneath it actually works, and a gate that fails the build when it stops working.

## The problem with "it seems to work"

A RAG pipeline gives you a lot of knobs and very little feedback. Mine started with the parameters you would expect: a weighted blend of semantic and keyword search, ten candidates narrowed to five by a second model. Every one of those numbers was a guess. I had no answer to _"does the re-ranking stage earn its latency?"_ or _"would keyword search alone be just as good?"_, and nothing would have told me if a change to how documents get split quietly broke retrieval.

That is the situation evaluation exists for, and it is not specific to this project. Any system whose output is text has the same problem: it is always producing something plausible, so "it seems to work" is the default state whether it works or not. The only way out is to decide in advance what good means, label enough ground truth to measure it, and put the measurement somewhere it can fail.

## How I decided what "good" means

**The golden set** is a set of questions of the kind a recruiter, hiring manager, or technical interviewer actually asks — employment history, specific technologies, project details, education, logistics. Each one is labelled with the phrases a correct answer has to be grounded in.

Labelling by _phrase_ rather than by document ID is the decision I would defend hardest. The corpus gets re-split every time I edit a source document, so any label tied to a chunk's identity is invalidated on every rebuild — the labels would rot faster than I could maintain them. Phrases survive re-chunking, which is what makes the golden set an asset rather than a chore.

**The metrics** are chosen for what they decide, not for what is easy to report:

- **hit@5** — did _any_ relevant passage reach the model? This is the one that gates the build, because it is what determines whether the system can answer at all.
- **recall@5** — what share of the relevant passages made it. Reported, deliberately not gated: several questions have more than five relevant passages, so their recall is capped below 1.0 by construction and no honest threshold could ever be met. A metric you cannot set a fair threshold on is a metric you should not gate on.
- **MRR** and **nDCG@5** — how far up the list the good passage landed, which matters because a model attends unevenly across a long context.

The thresholds sit _below_ measured performance with headroom for noise. They are floors, not targets. Tuning parameters until a floor is cleared would be fitting to my own test set, which produces numbers that look better and mean less.

**The questions are split** into a development portion and a held-out portion, and the table below reports the held-out one. Choices about the architecture are made against the development questions; the held-out questions are never looked at while making one. It is a smaller sample and therefore a coarser number, and I would rather publish a coarse number that means what it says than a precise one that is really the score of whatever configuration won on the questions used to pick it. The split is assigned by hashing each question's ID, so I cannot move an inconvenient question across the line without it showing up in a test.

Two of those entries share a pattern I found useful to learn: the code looked correct, every component behaved exactly as specified, every test passed, and nothing was going to surface the problem except a number moving. Unit tests tell you the parts do what you said; only measurement tells you the system does what you meant.

The third one is the one I would actually want to be asked about. I built a hybrid retrieval pipeline — semantic search fused with keyword search, then a cross-encoder re-ranking the candidates — because that is the architecture you build when you are demonstrating that you can build it. The evaluation said plain keyword search beat it on every metric. The tempting response was to retune the fusion weights until the numbers came back, and that would have been the wrong experiment: under the fusion formula I was using, tuning the semantic weight toward zero and switching the semantic stage off are the same experiment, so "find the optimal ratio" would have been a slower path to the answer I already had, ending in a magic constant with nothing behind it. So I ran the experiment that actually asked the question — keyword candidates fed straight to the re-ranker, no semantic stage at all — and it beat the full pipeline. Then the re-ranker failed the same test against keyword search alone.

The fix was to delete the architecture. Production retrieval is now keyword search and nothing else, which cut the backend from 87 production dependencies to 40 and the deployed container image from 17.2GB to 544MB. Most of that was not the model weights — it was `torch`, which the embedding library pulls in, and whose default Linux wheels ship the NVIDIA CUDA runtime into a container that has no GPU. I had been deploying several gigabytes of GPU libraries to serve keyword search, and nothing was ever going to tell me that except deciding the stage that needed them had not earned its place. Cheaper _and_ better is a stronger result than a tuned constant, and it is not the result I wanted when I started. Every deleted stage is still measured as a configuration on every run, because this corpus is written as anticipated questions and answers — the exact condition that flatters keyword matching — and I expect that to stop being true as the corpus grows. When it does, I want the harness to be what tells me, not a rebuild from scratch.

## Engineering around it

The eval is a CI gate, not a notebook. It runs on every backend change and fails the build if the shipped configuration drops below its floor, so retrieval quality cannot regress silently between commits. The other configurations are measured and published for comparison but not gated: a floor exists to stop a change degrading what a visitor is served, and nothing is served by a configuration production does not run. Because production is now keyword-only, the gate itself runs in seconds and needs no model weights at all.

The rest of the pipeline is held to the same standard. Ruff, ESLint, Prettier, and `tsc` gate every push. CodeQL, gitleaks, `pip-audit`, `npm audit`, and dependency review run on every pull request and weekly against unchanged code. Lighthouse CI watches performance and accessibility budgets. Every check lives in `scripts/` and is shared verbatim between the Makefile and GitHub Actions, so `make ci-cd` reproduces the PR gates exactly — no drift between what passes locally and what passes in CI.

One gate is there because of a specific mistake. My resume is a source document for the index, and it carried my home address and phone number, which meant the chatbot would read them back to anyone who asked. The fix was three-layered: strip it at the source, redact it during the index build as a backstop, and add a regression test that fails the build if a phone number or street address ever appears in the committed index again. The redaction and the detection are deliberately asymmetric — the redactor is precise, because rewriting the corpus silently means a false positive destroys real content unnoticed, while the test guard casts a wide net, because its only power is to fail a build and a false positive there costs one glance from me.

## What I am not claiming

The corpus is small, and much of it is written as anticipated questions with answers — which is exactly the condition that favours keyword matching over semantic search. Relevance is also labelled by exact phrase presence, which is close to what keyword ranking measures. Every configuration is scored against identical labels, so the comparison is internally fair, but any conclusion it supports is about _this_ corpus rather than about retrieval in general.

That bias cuts directly against the conclusion I drew from it, which is why the retired configurations are still measured rather than deleted from the harness: the result that told me to remove them is the same result I expect to reverse as the corpus grows past the point where the questions and the documents share vocabulary.

I would rather state that plainly than let a table imply more than it earned. The full write-up of the method, the biases, and what is still unmeasured — generation faithfulness, refusal behaviour on out-of-scope questions, adversarial robustness — is in the repository.

## Skills Demonstrated

The RAG pipeline is the part that looks impressive. The evaluation suite is the part that matters, and it is the difference between an engineer who assembles components and one who can tell you whether the assembly works.

This project shows I can define what "good" means for a system whose output is text, label ground truth in a form that survives the corpus changing underneath it, hold a portion of it back so published numbers are not tuned numbers, choose metrics for what they decide rather than what is easy to report, wire the result into CI as a gate rather than a report — and build the publishing path so that the conclusions stay honest as the system evolves, including the time the measurement contradicted the architecture I had already built and the right answer was to delete it.
